Rails応用は、難易度が高い。
自動販売機をコードで表現したものであり、 class VendingMachine に stock（在庫）,change（お釣り）,などの機能を持たせているので、それぞれの機能ごとに分けるという課題である。
本日、取り組んだのは
「プリミティブ型と文字型をラップする」
「ファーストクラスコレクションを使用する」
「Getter,Setter,プロパティを使用しない」
の３課題である。
正直にいうと、半分も理解していない。
何度も読み返したりすることで身に付く知識であると思っている。

まず、一つ目の「プリミティブ型と文字型をラップする」について。
実装前のコードは、VendingMachineクラスに、在庫、コイン、ドリンクの種類を管理する機能を持たせていた。
在庫、コインは整数値、ドリンクの種類については、定数で管理していた。
だが、Stock,Coin,DrinkTypeクラスを作成し、管理を委譲した。
よく聞く、オブジェクト指向である。
単なる整数値ではなくなり、意味のある値になるのだという。（理解していない）

続いて「ファーストクラスコレクション」について
配列をラップすることである（今日、覚えた言葉）
つまり、配列をそのまま使うのではなく、専用のクラスで包む（ラップ）することである。
まず、１００円硬貨の在庫を管理する class StockOf100Yen を用意する。
そこで initialize に配列と、add,size,popというメソッドを定義する。
さらに、お釣りを管理する class Change を用意する。
同様に initialize に配列を用意し、add,add_all,amount,clear,clone,to_sメソッドを定義する。
正直、何をやっているのか完全に理解できない。
なんとなく感じるのは、class を分けることによって、保守性が上がるのかな。というくらいだ。
あと、拡張が容易であるという点。
ただの配列に意味を持たせて、ルールを設けたというような感じなのか、、、
定義したメソッドは、中身を知らなくてもメソッド名で処理が分かるということか。

GPTによると
たとえば「自販機が在庫係（Stock）にこう言う」シーンを想像して：

❌「お前の @quantity が 0 かどうか教えろ」
✅「在庫切れかどうか教えて」

後者のほうが自然やろ？
前者は在庫係の内部の変数名にまで依存してて気持ち悪い。
（もし在庫係が管理方法を変えたら、自販機は混乱して壊れる💥）

⸻

つまり一言で言うと：

empty? にすることで、
「Stockがどう在庫を持っているか」という実装の自由度を守りながら、
呼び出す側には“意図だけ伝える”ことができる。

とのこと。
結局、書いていたコードを別のクラスに移して、メソッド名で分かりやすくしているということ。
そうすれば、変更に強く、メソッドの中身を見なくても、メソッド名で何をしているかわかる。

「Getter,Setter,プロパティを使用しない」についても結論、「中のデータを直接触るな。結果だけ聞け。」である。
今日、やったことに全て通じるのは、これである。
それぞれで、実装方法が違うだけである。

正直、これまでのカリキュラムで一番難しいかもしれない（何回も言っている気がする）
これは、今日一日だけでは絶対に理解できない。
継続して学習し、リファクタリングが必要になったりした際、今回のカリキュラムを見返すのが良いのだと思う。
